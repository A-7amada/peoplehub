# ADR-0023: Staged full tenant isolation build

Status: Decided 2026-11-27 (owner decision relayed by the main agent from Ahmed, WhatsApp 01:56: go ahead with the staged full tenant isolation build, shared database, TenantId, filters, RLS). Builds on ADR-0001 to ADR-0004. Stage 0 exists. Stage 1 (isolation audit) built 2026-11-27, see "Stage 1 audit results"; later stages are not built yet.

## Where it stands (from the code)
- TenantId column on tenant-owned tables, global EF query filter on each, tenant stamped on save, `Tenant` table, `ITenantContext` (web: from the `tenant_id` claim, defaulting to tenant 1; jobs and tests: `FixedTenantContext`). `TenantIsolationTests` and `MaintenanceIsolationTests` exist.
- Not built: sign-in that issues the tenant claim per user, tenant creation and lifecycle, platform administration, per-tenant uniqueness review, per-tenant jobs and files audit, Postgres RLS, tenant-specific settings, subscriptions.

## Stages (each is a small pushed increment with the full gate)
1. Isolation audit: list every table, every raw SQL call, cache key, file path and setting for tenant leakage. Extend isolation tests to cover each module with two tenants. Fix findings.
2. Tenant-bound identity: users belong to one tenant; login resolves the tenant and issues the claim; uniqueness (email, employee code) becomes per tenant where required; cross-tenant access returns not found.
3. Tenant lifecycle: platform-tenant admin can create, suspend and archive a customer tenant with seed data and a first admin. Platform staff are separate from customer users (ADR-0004).
4. Per-tenant configuration: settings, workflows, leave and payroll policies, branding and language defaults resolved per tenant.
5. Postgres RLS as a second line of defence, applied through a session setting and verified against Neon on a branch first. SQLite stays on the filter only. This stage depends on a verified Neon run; if RLS cannot be verified on the free tier it stays documented as unverified.
6. Subscriptions and billing records (plans, status, limits) on the platform side, with no payment provider (no paid service).

## Consequences
The filter stays the primary control and RLS is the backstop. A bug in raw SQL or a missing filter would leak data, so each stage adds tests that run the same scenario as two tenants and assert zero cross-reads. Free-tier limits stay: no paid database per tenant, no paid billing provider.

## Stage 1 audit results (2026-11-27)
What was checked, from the code:
- Query filters: a model-wide test fails if any tenant-owned entity lacks a query filter (`TenantAuditTests`).
- Raw SQL and filter bypass: no `IgnoreQueryFilters`, `FromSql`, `ExecuteSql`, `ExecuteDelete` or `ExecuteUpdate` call exists in `src` outside migrations.
- Unique indexes: a model-wide test fails if a unique index on a tenant-owned table lacks `TenantId`, unless it is on a reviewed list. Reviewed and kept global: indexes made only of ids of tenant-owned rows (ids are unique database-wide, so they cannot collide across tenants) and random secrets (tokens, token hashes). Fixed in migration `TenantScopedUniques` (both providers, index changes only, no data change): `AppSetting(Key)`, `HrFieldDefinition(Label)`, `WorkflowRevision(Kind, Hash)`, `DevicePunch(IdempotencyKey)`, `IntegrationEvent(IdempotencyKey)` are now unique per tenant.
- Cache: the `ICache` path is tenant-keyed by `TenantKeyedCache`.
Open findings, carried to later stages (not fixed here):
- `AppUser(Email)` is still unique across the database. It becomes per tenant with the tenant-bound login in stage 2.
- `SettingsService.Cache` is a process-wide static dictionary keyed only by setting key, so a second tenant would read the first tenant's cached settings. It needs per-tenant keys with the per-tenant configuration work in stage 4. Until then only one tenant is in use.
- Files (stored in the database) and the internal scheduler's per-tenant job loop have not been audited yet for stage 1 and stay on the list.

## Stage 2 build status (2026-11-27): tenant-bound sign-in
Built: `AppUser(Email)` is unique per tenant (migration `TenantScopedLogin`, both providers, index changes only). The sign-in form takes an optional company (the tenant slug); blank means `demo`; an unknown or inactive company fails with the same message as a wrong password. The company field appears only when more than one active tenant exists, so the single-tenant demo looks unchanged. The signed cookie carries a `tenant_id` claim, the second-factor ticket carries the tenant, and cookie validation resolves the tenant from the claim before it looks up the user. Tested with a two-tenant login test (same email, different passwords, each signs into its own tenant only) and by hand on a local SQLite upgrade with the same email in two tenants.
Not done yet (stays on the list): forgot-password and reset-token flows still resolve in the default tenant, so users of other tenants cannot reset a password by email until they carry the company too; tenant lifecycle (creating tenants) is stage 3 and until then a second tenant exists only if inserted by hand; Postgres was not exercised.

## Stage 3 build status (2026-11-27): tenant lifecycle and platform staff
Built: `TenantProvisioner` creates a company in one transaction (the Tenant row, then roles, permissions, approval workflows, the four basic leave types ANN/SICK/CAS/UNP and one administrator with SystemAdmin and HRManager roles; no employees, no demo data). `TenantAdminService` lists, creates, suspends, reactivates and archives companies; every call needs a platform session. Slugs are 2 to 31 characters of lowercase letters, digits and hyphens, unique, with reserved names refused; the administrator password needs 8 characters with a letter and a digit. The default company cannot be suspended or archived. A suspended or archived company cannot sign in and its live sessions are rejected at the next request. Nothing is deleted.
Platform staff (`PlatformUser`, migration `PlatformUsers`, both providers) sign in separately at `/Platform/Login`, belong to no company and use a session that customer pages reject. The first platform admin is created at startup only when the optional settings `PLATFORM_ADMIN_EMAIL` and `PLATFORM_ADMIN_PASSWORD` are present. Five wrong passwords lock the account for 15 minutes.
Not done (stays on the list): platform staff second factor; a time-limited, audited support grant to read customer data (ADR-0004, not built); platform staff management screens; tenant data export or deletion; password reset for non-default companies; per-tenant settings cache (stage 4); Postgres row-level security (stage 5); subscriptions (stage 6). Tenant provisioning was exercised on SQLite only; the Postgres migration SQL was inspected, not run.

## Unit US-PH1-001 build status (2026-11-28): lifecycle audit
Every company create, suspend, reactivate and archive writes a PlatformAuditLog row: actor (platform staff email), UTC time, company id and short name, action, and a required reason (3 to 500 characters; a change without a reason is refused and nothing is logged). The table belongs to no company (not tenant-owned; the key column is CompanyId because the save hook stamps any column named TenantId). Only platform staff can read it, in the audit trail on /Platform. Migration PlatformAuditLog exists for SQLite and PostgreSQL (CreateTable plus an index on At). Customer audit logs are unchanged. Retention of this log and legal hold remain an owner-type default to record.

## Stage 4 build status (2026-11-28): per-company settings and reset links
- SettingsService keeps one cache per company. The company comes from the request (HttpTenantContext), and a company's saved settings are read once on first use and refreshed when that company saves. Before this, one process-wide cache meant one company's settings (password length, lockout, SMTP, device mode) applied to every company. Sign-in throttling values now follow the company being signed in to; the anonymous rate limiter policy reads the default company.
- Password reset links carry the company short name (&company=slug) and the Forgot and Reset pages resolve that company first, so a customer company's token is found under its own isolation filter. The Forgot page shows a company field only when more than one active company exists, like sign-in.
- Not part of stage 4 (still partial in the backlog audit): per-company workflows, leave and payroll policies, branding and language defaults beyond settings. Those already live in tenant-owned tables, so they are isolated, but there is no platform UI to edit them for another company; staff cannot read customer data by design (ADR-0004).

## Stage 5 status (2026-11-28): Postgres RLS written, not applied, not verified
docs/architecture/rls/postgres-rls.sql enables and forces row-level security with a tenant_isolation policy on every table that has a TenantId column. It is NOT applied and NOT verified: there is no Postgres instance in the build environment, a run on a Neon branch is needed, and the app must first set app.tenant_id on each connection (not built). Applying it earlier would hide all rows. The query filter remains the isolation mechanism in production. This item stays deferred until it can be verified (infra verification, not a spend item).
