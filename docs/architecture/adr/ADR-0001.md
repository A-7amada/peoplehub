# ADR-0001: Tenant data isolation: shared database with TenantId

**Status:** Accepted (2026-11-25 22:50, Ahmed). Implementation status is tracked in BLUEPRINT.md.

## Context
Single-tenant today. Ahmed confirmed SaaS multi-tenant on 2026-11-25.

## Decision
Every table that holds customer data gets a TenantId column. A global EF Core query filter applies it to every query and the tenant is stamped on save. Platform tables (tenants, subscriptions, system settings) have no TenantId. Postgres Row Level Security is evaluated as a second line of defence once verified on Neon. The code stays able to move one large customer to its own database later (hybrid).

## Alternatives considered
Schema per tenant (harder migrations, awkward on Neon Free). Database per tenant (strongest isolation, higher cost and operations; kept as the later option for large customers).

## Consequences
Cheap to run, simple migrations. Risk: a raw query that bypasses the filter. Mitigation: isolation tests (ADR-0017) and a ban on raw SQL outside Infrastructure.

## Design patterns used
Pattern: Multi-tenant shared schema, Specification via global query filter.
