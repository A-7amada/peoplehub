# ADR-0020: API conventions and OIDC preparation

Status: Accepted as a convention 2026-11-26 (approved step 8 of the Phase 0 order). Not yet built as endpoints: today the only API is the device ingest endpoint (`/api/device`). Nothing below adds a paid service.

## Conventions (apply to every new `/api/v1` endpoint)
- Versioned path `/api/v1/...`. A breaking change gets `/api/v2`; v1 stays until its callers are gone.
- Errors use `application/problem+json` (RFC 9457) with a stable `code` (the same message keys the UI uses, for example `err.reasonRequired`), the correlation id (`X-Correlation-ID`, already sent on every response) and no stack traces.
- Writes that an external system may retry take an `Idempotency-Key` header. The key and request hash are stored with the response for 24 hours; the same key with a different body is a 422.
- Concurrency uses the existing `Revision` token: `If-Match` on updates, 409 on a stale token (already how the web app behaves).
- List endpoints page with `limit` and an opaque `cursor`, never offsets.
- Tenant comes from the authenticated principal (`tenant` claim), never from a request field. The `ITenantContext` seam is already in place.
- Authorization reuses the same permission checks as the web app. Device keys stay separate and scoped to ingest only.

## OIDC preparation
- Identity providers sit behind one seam (Strategy). Local email and password stays as the demo provider.
- An external OIDC provider (Entra ID, Google Workspace, Auth0 or Keycloak) is a spend or hosting decision for Ahmed. Preparation here is limited to: the tenant claim name above, the rule that a user is matched by verified email within a tenant, and no provider-specific code in Application or Domain.
- Not built: tenant claim issued at login, provider configuration per tenant, account linking.

## Consequences
Cheap to follow now, expensive to retrofit. Review of the problem+json code list and idempotency retention belongs with the specialist review already flagged.
