# ADR-0021: Sensitive field encryption (free, app level)

Status: Proposed 2026-11-26. Scope instruction came through Main from the owner's 12:04 voice messages: start now, free approach only (app-level authenticated encryption, key from the environment, key custody documented, no paid key service). Specialist review is deferred by the owner and stays open.

## Decision
- **Algorithm:** AES-256-GCM, a fresh random 96-bit nonce per value, authenticated with the table and column name as associated data (a ciphertext copied into another column fails to decrypt).
- **Envelope:** `enc:v1:<keyId>:<base64(nonce|ciphertext|tag)>`. Values without the `enc:` prefix are read as legacy plaintext, so rollout needs no big-bang migration and a half-finished backfill is safe.
- **Seam:** one EF Core `ValueConverter` (Strategy/Decorator on the property mapping). Domain and services keep working with plain strings. Applied per property in `AppDbContext` from one list, so the covered fields are visible in one place.
- **Key source:** `FIELD_ENCRYPTION_KEY` environment variable (any secret string; the 256-bit key is derived with HKDF-SHA256). Previous keys go in `FIELD_ENCRYPTION_KEY_PREVIOUS` (comma separated, same format) so values written under an old key stay readable while they are re-encrypted. Key id is the first 8 hex chars of SHA-256 of the derived key.
- **No key set:** the app runs exactly as today (plaintext) and `/health/ready` details and the Settings page say encryption is off. Setting a key turns on encryption for new writes; a backfill command re-encrypts existing rows.
- **Order of rollout (small increments):** 1. key service + converter + tests + TOTP seed. 2. Employee national id and IBAN, payroll IBAN snapshots. 3. Backfill command and Settings status. 4. Rotation command (`re-encrypt with current key`). Documents/files in the database are a later increment: they need streaming encryption, not a column converter.

## Key custody (the limits are real)
- Production key: generated once, stored as a vault secret by the platform (never printed), set as the `FIELD_ENCRYPTION_KEY` environment variable on Render. **Escrow:** the owner can reveal that vault copy once through the vault's own one-time link; keep it offline. If the key is lost, encrypted fields are unrecoverable. Backups hold ciphertext only and are useless without the key.
- Protects against: a leaked database, a leaked backup, a Neon or SQL-level read. Does **not** protect against: a compromise of the running app or of the Render environment (the key is there), an administrator with Render access, or anyone who can call the app as an authorised user.
- Not provided: hardware key storage, automatic rotation, split knowledge, audit of key use, searching or sorting on an encrypted column (the converter makes these impossible, so covered fields must not be filtered in SQL; a test guards this).
- Free-tier deviation kept: no paid key service. A paid KMS (for example a managed key vault) is the upgrade path and is a spend decision for the owner. Specialist review of the scheme is deferred.

## Consequences
Encrypted columns grow by about 45 percent. Equality lookups on covered fields stop working (none exist today for national id or IBAN). A wrong or missing key makes covered fields unreadable, so the app fails closed with a clear error instead of showing ciphertext.
